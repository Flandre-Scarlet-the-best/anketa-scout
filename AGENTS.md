# Anketa Scout: инструкции агентам

Anketa Scout — кроссплатформенное Rust CLI-приложение для обработки анкет с расширяемыми источниками. Фактическое состояние реализации описывает [DEVELOPMENT.md](.codex/context/DEVELOPMENT.md); проектные решения не означают, что функциональность уже реализована.

## Глобальные инварианты

- Общение, собственная документация, комментарии, логи, сообщения пользователю, коммиты и PR — на русском. В Conventional Commits тип и scope остаются английскими. Имена API, идентификаторы и машинные контракты не переводить.
- Прикладная реализация — Rust. Не добавлять Bash/SH, PowerShell, Batch/CMD или другие shell-обёртки. Нетривиальная постоянная проверочная автоматизация при необходимости также пишется на Rust. Не создавать инфраструктуру «на будущее» без применимого сценария.
- Сохранять чужие изменения, работать только в области поручения, не выполнять разрушительные Git-операции без отдельного разрешения.
- Контакты, исходные посты, конфиги с секретами, локальные снимки и сырой ответ источника не публиковать в Git, PR, Gist, логах или диагностике. Проверять содержимое, а не полагаться на `.gitignore`.
- Отделять факты, подтверждённые по конкретному SHA и исполненным командам, от допущений. Не объявлять зелёным незапущенную проверку. Не подменять реальные проверки тестовым симулятором.
- CodeRabbit запускается **только по отдельному положительному поручению**. Обычное «проверь код», упоминание CodeRabbit или изменение skill не разрешают запуск. Независимое ревью не является CodeRabbit.
- Для публикуемой задачи по умолчанию доводить изменения до подтверждённых commit → push → Draft PR; Ready/merge/release никогда не выводятся из успешного CI. Уточнения и исключения принадлежат `scout-git-workflow`.

## Маршрутизация и владельцы

1. Прочитать [индекс владельцев](.codex/context/INDEX.md) и выбрать относящиеся к изменению документы, не загружая всё подряд.
2. Изменять правило только у его канонического владельца: архитектуру — в `ARCHITECTURE.md`, разработку — в `DEVELOPMENT.md`, верификацию — в `VERIFICATION.md`, версии — в `VERSIONING.md`, рабочую процедуру — в соответствующем skill.
3. Для Git/GitHub использовать `scout-git-workflow`; для независимого ревью — `scout-code-review`; для явно запрошенного внешнего ревью — `scout-coderabbit-review`.
4. Канонические skills — `.agents/skills/*/SKILL.md`, входы Claude Code — `.claude/skills/*/SKILL.md`. Вход Claude ссылается на канонический skill, не содержит второй копии процедуры.
5. В конце указать точные изменённые файлы, проверенную ревизию, результаты, ограничения и ссылку на опубликованный Draft PR, когда поручена публикация. Не скрывать неустранённые замечания.
