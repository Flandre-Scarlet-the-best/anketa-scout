# Политика доказанных замечаний

## Порог доказательства

Каждое замечание обязано содержать:
1. точный файл/строку или воспроизводимую точку контракта;
2. вход/условия, при которых проблема проявляется;
3. ожидаемое поведение и реально нарушенное требование;
4. последствия для пользователя, данных, безопасности или переноса;
5. тяжесть и конкретное направление исправления.

Без причинной цепочки — гипотеза или вопрос, а не подтверждённый дефект. Не увеличивать количество находок разделением одной первопричины на несколько. Ненужные стилистические пожелания не превращать в дефекты.

## Серьёзность

- **Critical** — вероятная потеря/публикация приватных данных, эксплуатация, небезопасная запись либо широкая поломка без обхода; блокер.
- **Major** — доказанная существенная ошибка корректности, регрессия, невыполнение явного требования или несовместимость, обычно блокирует принятие.
- **Minor** — ограниченный воспроизводимый дефект с меньшим ущербом; исправление желательно, не всегда блокер.
- **Trivial** — объективное неблокирующее несоответствие действующему контракту. Не заводить ради вкуса.

Отдельно обозначать значимость: высокий риск при недоказанном сценарии требует проверки, а не искусственного присвоения Critical.

## Статус ревью

- `REQUEST_CHANGES` — есть подтверждённые блокирующие замечания.
- `COMMENT` — существенная область проверена, есть только неблокирующие находки либо уточнения.
- `CLEAN` — подтверждённых находок нет, задача, diff, значимый окружающий код и обязательные проверки достаточно охвачены.
- `INCOMPLETE` — критичные требования, часть diff, окружающий код, инструмент или обязательная проверка недоступны; «нет находок» не значит CLEAN.

`CLEAN` — результат проверенного охвата, а не математическая гарантия. Для недоступных проверок указать конкретную причину и влияние на вывод, не повышать уверенность формулировками.
