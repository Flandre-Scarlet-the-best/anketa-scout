# Производительность и регрессии

## Маршрутизация

Применять, когда задача обещает ускорение, уменьшение памяти, увеличение пропускной способности или явно требует сравнить производительность существующей операции. Обычные исправления и простой тестовый запуск не становятся бенчмаркингом. Методология находится в [measurement-policy.md](references/measurement-policy.md); не создавать инфраструктуру измерений заранее.

## Главные инварианты

1. **Нет сопоставимой базы — нет доказанного ускорения.** Нельзя сравнивать разное содержимое живого треда, разные настройки и окружения без пометки о несопоставимости.
2. Замерять **действительно исполненный** путь именно той ревизии, о которой делается вывод. Связать бинарник, сборку, вход и SHA. Совпадение HEAD само по себе недостаточно.
3. Фиксировать условия: платформа, CPU, RAM, Rust/toolchain, профиль сборки, размер и идентичность входа, прогрев, кэш, сеть, количество повторов и разброс.
4. Сначала функциональная корректность и безопасность, только затем скорость. Нельзя ради оптимизации обходить проверку контактов, лимиты, безопасность вывода или обработку ошибок.
5. Не публиковать контакты/посты/личные снимки. Для воспроизводимости предпочтительны синтетические данные; внешний источник не годится как стабильная нагрузка.
6. Бенчмарк не редактирует Git/GitHub и не обновляет показатели в README без отдельного поручения. Публикация через `scout-git-workflow`.

## Результат

В `Производительность` PR выводить короткую сводку: измерено/не измерено, базовая и новая ревизии, нагрузка, единицы, медиана или иная заранее выбранная метрика, разброс, изменение и существенные ограничения. Не превращать численный шум в реальную регрессию.
