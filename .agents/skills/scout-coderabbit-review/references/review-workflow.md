# Выполнение цикла CodeRabbit

## 1. Объект, область и чистота

Зафиксировать текущие git root/repo, branch, HEAD, рабочие изменения и точные base/head PR. Убедиться, что локальная рабочая копия относится к требуемому PR; не подменять её другой веткой. Новый candidate для опубликованного ревью требует соответствующего push и проверки remote ref. Dirty worktree оценивать отдельно: не перемешивать его с опубликованным diff, не обещать, что провайдер видел незакоммиченные файлы.

Отсутствие подходящего PR или расхождение локального/удалённого SHA — остановка до исправления идентичности, а не повод перейти в соседний репозиторий.

## 2. Фактический интерфейс провайдера

Проверить доступность и авторизацию CLI, версии и реальный `--help`; не угадывать флаги из старых инструкций. Если конфигурация менялась, проверить `.coderabbit.yaml` по официальной JSON Schema (правило выбора проверки принадлежит `VERIFICATION.md`). Не выполнять установку/апгрейд как побочный эффект ревью. Для Windows не подменять локальный native CLI на WSL/облачное ревью без согласования.

Выбрать явные base/source/head и режим согласно текущей версии провайдера. Проверить, что scope покрывает изменения, а не пустой diff. Пользовательский deep/fresh не снижать молча до обычного. При недоступной опции сообщить препятствие и уточнить отдельным решением, не засчитывая неисполненный проход.

## 3. Итерация

Целевое количество `N = положительное число пользователя, иначе 3`. Для каждого прохода:

0. **Восстановление перед запуском.** Перечитать таблицу PR, удалённый HEAD и локальную запись завершённых проходов (п. 3). Если есть завершённый проход, не отражённый в таблице, или опубликованный commit исправлений без своей строки, сначала дописать их по сохранённой записи через `scout-git-workflow` и не запускать платный повтор того же candidate. Если записи нет, а признаки завершения есть (новые commit, сообщения сессии), установить фактический исход по выводу и истории провайдера; при невозможности — сообщить пользователю, а не повторять вслепую.
1. Зафиксировать точный опубликованный candidate и базу; подтвердить отсутствие неучтённых изменений.
2. Запустить согласованный режим CLI на **этом** candidate. Не запускать неограниченные платные retry.
3. Дождаться **фактического полного завершения** и проверить код/статус, итоговые метаданные, отсутствие признаков partial/failure, coverage scope. Наличие отдельных замечаний, обрыв stdout, `SKIPPED` или `0 findings` без подтверждённого завершения не дают clean pass. Сразу после подтверждения завершения сохранить вне Git (во временном каталоге сессии) запись прохода: reviewed HEAD, режим, идентификатор запуска, если провайдер его выдаёт, и находки — без контактов и секретов.
4. Независимо проверить каждую находку по diff, контракту, окружению и тестам; классифицировать: подтверждена, частично подтверждена, повтор, устарела, ложная/неприменимая, требует данных. Сохранить техническое основание.
5. Исправить подтверждённое **в пределах поручения**, выполнить применимые проверки. Не менять правила безопасности/тесты ради зелёного результата.
6. Если появились подтверждённые изменения, подготовить их и проверки к передаче в `scout-git-workflow` для commit и публикации. Если исправлений нет, не создавать пустой commit или иные фиктивные изменения ради галочки.
7. Передать `scout-git-workflow` данные для **новой строки** накопительной таблицы CodeRabbit. Поручить ему при наличии исправлений выполнить commit/push и проверить удалённый SHA, обновить PR body без удаления предыдущих строк и перечитать PR body и удалённый HEAD. Если исправлений не было, HEAD остаётся тем же; следующую итерацию запускать на этом же опубликованном candidate после повторной проверки его идентичности.
8. Только после полного прогона, независимого triage, необходимых исправлений и read-back PR через владельца публикации увеличить счётчик завершённых итераций.

Не завершать на первой clean итерации, если `N` больше единицы. Не создавать искусственные находки, чтобы получить commit. Не пересматривать старую итерацию задним числом, если HEAD изменился.

## 4. Недостаточная область и лимиты

- Пустой scope/неправильная база: не засчитывать итерацию; исправить выбор ревизий, подтвердить новую область.
- Rate limit: использовать только явно сообщённые провайдером пределы и время. Если продолжение сейчас недоступно, остановиться, передать `completed/N`; не выдавать planned retry за выполненный.
- Обрыв/ошибка CLI/таймаут/partial: не засчитывать, не маскировать ложным clean. Перед повтором проверить фактическое состояние и не дублировать побочные эффекты.
- Deep review, не поддерживаемое провайдером: не заменять обычным без поручения.
- Невозможно безопасно передать исходники/контакты: прекратить небезопасный шаг; указывать причину и альтернативы без раскрытия данных.

## 5. Содержательное заключение

В `## CodeRabbit review и disposition` оставлять только одну накопительную таблицу по образцу [PR #26](https://github.com/Flandre-Scarlet-the-best/anki-deck-toolkit/pull/26), с колонками:

| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |

Для каждой находки добавлять отдельную строку. В первой ячейке указывать номер прохода, короткий reviewed HEAD и режим (`simple`, `deep` или `deep + fresh`); в остальных — уровень CodeRabbit, путь, конкретное влияние, независимое решение и краткое исправление с SHA опубликованного commit. Решение маркировать `confirmed`, `partially confirmed`, `duplicate`, `stale`, `rejected` или `needs evidence`, добавляя короткое основание для частичного подтверждения, повтора, отклонения или нехватки данных.

Если завершённый проход не дал находок, добавлять одну строку с теми же номером, reviewed HEAD и режимом, уровнем и путём `—`, итогом «замечаний нет», решением `clean` и исправлением `—`. Незавершённые попытки отражать как `incomplete` с причиной, не включая их в номер завершённой итерации.

Если очередная строка не помещается в лимит тела PR (10 000 символов, см. [pr-body.md](../../scout-git-workflow/references/pr-body.md)), сжимать самые ранние завершённые итерации до одной строки на итерацию: номер, reviewed HEAD, режим, число находок по решениям и SHA исправлений. Итерации не удалять; подробности сжатых строк остаются в review-комментариях провайдера и commit. Проверки размещать в `Проверки`, статусы GitHub — в `CI`; в разделе disposition оставлять только таблицу.

Отдельно указать ограничения, незавершённые попытки и причины, по которым они не зачтены. После каждого прохода подтверждать PR body по read-back.

В пользовательском ответе указать число `completed/N`, точную проверенную ревизию, status CI и препятствия. Ни один статус CodeRabbit не разрешает автоматический merge.
