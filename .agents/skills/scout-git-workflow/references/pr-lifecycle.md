# Жизненный цикл PR, Ready, merge и cleanup

## Поиск и создание

1. Найти существующие открытые PR по **репозиторию, base и head**; проверить результаты полностью, включая авторство и форк, не выбирать по похожему заголовку.
2. Если подходящий PR есть, обновлять его. Не создавать второй ради нового commit. Если отсутствует — создать Draft с подготовленным валидным описанием.
3. Перед записью описания перечитать актуальную базу и head. Многострочный текст передавать через структурированный GitHub API или `gh pr create/edit --body-file` и **проверить факт записи**.
4. После изменения повторно прочитать PR и сравнить: URL, номер, repo/base/head, sha, Draft, заголовок, тело, статус GitHub checks. Несовпадение требует устранения либо сообщения об ограничении.
5. Если изменилась база и устарело сравнение, повторить проверку diff, версионного решения и применимых тестов. Не утверждать, что прежняя ревизия проверена за новую.

## Ready

Перевод в Ready **только после отдельного разрешения**. Перед этим проверить фактический HEAD, актуальность базы, полноту body, обязательные checks, существующие замечания и блокеры. Наличие Draft или зелёного CI не означает готовности. Если правило защиты ветки не требует checks, **не считать** это доказательством прохождения и явно сообщать риск.

## Merge

Слияние **только по отдельной текущей команде пользователя**. Повторно установить точный PR, owner/repo, base/head, Draft/Ready, ветку, mergeability, комментарии и ревью, все применимые required status checks и дополнительные заданные checks. Состояния `pending`, `skipped` и `neutral` интерпретировать по фактическим правилам GitHub и согласованному критерию; не объявлять их зелёными по умолчанию. При обновлении HEAD начать проверки заново. Сначала устранить блокеры; не отключать ruleset, не обходить required checks, не применять forced/admin merge без нового разрешения.

При конфликте с `main` выбрать безопасное разрешение с сохранением обоих изменений; не переписывать опубликованную историю без основания. Семантический конфликт, где нужно решение пользователя, не маскировать техническим merge.

## Cleanup

После подтверждённого merge сверить GitHub-состояние, убедиться, что нужные коммиты вошли в основную ветку. Удалять только точно установленную **собственную** рабочую ветку и только если это допустимо поручением; не очищать чужое рабочее дерево. Передать пользователю реальные итоги и ограничения.
