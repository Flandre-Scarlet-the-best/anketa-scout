# Публикация: branch, индекс, commit, push и удалённый результат

## 1. Состояние и идентичность

Установить Git root, `origin`, default branch, текущую ветку, локальный и удалённый HEAD, upstream, `git status --short`, staged/unstaged diff и untracked. Не предполагать, что имя папки или текущий remote совпадают с порученным репозиторием. Работа при неизвестных локальных изменениях не должна их уничтожать или подмешивать.

Для новой самостоятельной задачи создать ветку от актуального `origin/main` после чтения источника. При продолжении задачи найти и подтвердить уже существующую ветку и PR; не создавать дубль по умолчанию. Переключение между ветками объяснить до действия.

## 2. Подготовка изменений

Изучить изменённый и окружающий код, документацию и применимые правила. Перед коммитом выполнить проверки по [VERIFICATION.md](../../../../.codex/context/VERIFICATION.md), перечитать **весь** diff, выбрать пути явно, выполнить `git diff --cached --check` и `git diff --cached`. Не индексировать всё дерево автоматически при посторонних изменениях. Отдельно проверить приватные и локальные данные, бинарные файлы и изменение workflow/rulesets. Если обязательная проверка не выполнена — сообщить это в PR, не писать «успешно».

## 3. Commit и push

Создать содержательный Conventional Commit; до отправки убедиться в ожидаемом `git rev-parse HEAD`. Для push использовать явный `origin` и текущую рабочую ветку; не применять `--force` и не обновлять `main`.

После push считать фактический SHA `refs/heads/<branch>` через `git ls-remote` или GitHub API. Сравнить его с локальным HEAD. Успешный код команды или локальный `origin/<branch>` — не подтверждение удалённого результата.

## 4. Неизвестный результат сети

Если timeout/обрыв/5xx/невнятный ответ произошёл при create/push/update, **не повторять действие автоматически**. Сначала перечитать через независимый GET фактический ref/PR/body:
- удалённый ref уже равен ожидаемому SHA → запись произошла, продолжить без дубликата;
- удалённый ref равен прежнему SHA → можно осторожно повторить при неизменных предусловиях;
- удалённый ref отличается от обоих → остановиться, сохранить чужой результат и разобраться без force-push;
- ответ получить нельзя → зафиксировать неизвестный исход, не объявлять публикацию успешной.

Для GitHub API без локального checkout применять ту же модель: зафиксировать базовый SHA, создавать commit с правильным родителем, передвигать только созданную рабочую ветку с проверкой ожидаемого SHA, повторно читать её HEAD.

## 5. Завершение

Передать [pr-lifecycle.md](pr-lifecycle.md) подтверждённые owner/repo, base/head, commit SHA, сводку реальных проверок и ограничения. Отдельные сообщения пользователя «теперь push» не требуются для обычной публикуемой задачи.
