# Жизненный цикл Git/GitHub

## Назначение и владение

Единственный владелец изменяющей процедуры Git/GitHub. Содержимое правок определяет задача и [контекст](../../../.codex/context/INDEX.md), необходимые проверки — [VERIFICATION.md](../../../.codex/context/VERIFICATION.md), SemVer — [VERSIONING.md](../../../.codex/context/VERSIONING.md). CodeRabbit и независимое ревью **не заменяют** Git-процедуру.

## Маршрутизация

Вызывай для подготовки ветки, commit, push, создания/обновления PR, Ready, отдельно разрешённого merge, разрешения конфликта и cleanup. Не вызывай ради простого чтения чужого PR, объяснения Git или только ревью без публикации.

**Обычная публикуемая задача завершается не локальным коммитом, а проверенным удалённым состоянием:**
изменения → применимые проверки → подготовленный и перечитанный индекс → commit → push → точная проверка удалённого SHA → создать или обновить Draft PR → сверить опубликованный PR с HEAD → передать пользователю.

Если пользователь явно сказал «только локально», «не push» или «только commit», сократить цепочку ровно в разрешённой части. Merge/Ready/release **не** следуют автоматически даже из зелёного CI.

## Инварианты

- Одна самостоятельная задача — одна ветка и PR. Существующую ветку задачи продолжать, не создавать дубль. Не работать напрямую в `main`.
- Перед сменой ветки установить текущее рабочее дерево и сохранить чужие изменения; не переключаться молча.
- Читать реальный diff и staged diff, добавлять в индекс только явные пути задачи. Контакты, локальные снимки и секреты не отправлять.
- Сообщение commit — Conventional Commits с русским смысловым описанием; не создавать фиктивных изменений ради галочки.
- Проверка успешности push по коду возврата недостаточна: требуется удалённая ссылка `refs/heads/<branch>` и точное сравнение с ожидаемым SHA. При неизвестном результате сначала **читать** удалённое состояние, а не повторять запись вслепую.
- Проверять репозиторий, base/head, точный HEAD, Draft, заголовок, тело и проверки **после** публикации.
- При изменении `main` или HEAD результаты старых проверок пересматривать. Зелёный CI предыдущего SHA не является CI текущего.
- Force-push, удаление чужих веток, переписывание истории, прямой push в main, Ready, merge и Release требуют отдельного явного разрешения и проверки предусловий.
- Не ослаблять CI/ruleset ради зелёного результата, не создавать подставные статусы.
- Не создавать отдельный журнал публикации, Git-обёртку или второй источник PR body.
