# Жизненный цикл Git/GitHub

Это единственный владелец процедуры публикации. Проверки выбираются по
[VERIFICATION.md](../../../.codex/context/VERIFICATION.md), решение о версии — по
[VERSIONING.md](../../../.codex/context/VERSIONING.md).

1. Установить репозиторий, удалённый репозиторий, ветку, upstream, состояние рабочего
   дерева, актуальные main и HEAD.
   Одна самостоятельная задача — одна рабочая ветка и PR; не менять main напрямую.
   Перед переключением объяснить выбранную ветку, сохранить чужие изменения.
   Для начатой задачи продолжать её ветку, не создавать дубль.
2. Изучить diff относительно актуальной базы и незакоммиченные файлы. Выполнить
   применимые проверки. Добавить в индекс только явные пути задачи, перечитать
   `git diff --cached` и проверить отсутствие приватных данных и случайных файлов.
3. Сделать коммит с русским описанием в Conventional Commits. Без явного ограничения
   «только локально» / «не отправлять изменения» продолжить до публикации,
   не останавливаться на коммите.
4. Отправить рабочую ветку. Сравнить локальный `git rev-parse HEAD` с SHA фактического
   `refs/heads/<ветка>` через `git ls-remote`, а не только с локальной ссылкой отслеживания.
   При сетевой неопределённости сначала прочитать удалённое состояние; не повторять
   мутацию вслепую и не использовать force-push для обхода расхождения.
5. Найти PR по репозиторию, базовой и рабочей веткам, создать или обновить именно
   его как Draft.
   Использовать `gh` или подходящий структурированный GitHub API. Многострочное тело
   передавать структурированно либо через временный UTF-8 файл и `--body-file`.
6. Перечитать опубликованный PR: репозиторий, базовую и рабочую ветки, точный SHA
   рабочей ревизии, статус Draft, заголовок, тело и фактические проверки GitHub.
   Проверить, что main не изменился так,
   что устарели выводы о diff или версии; при изменении пересмотреть их.
   Отсутствие проверок назвать отсутствием CI. При исправлениях повторить необходимые
   проверки и публикацию; старое ревью не относится автоматически к новому HEAD.
7. Передать пользователю ссылку на Draft PR, результат и ограничения. Не переводить
   в Ready, не сливать PR и не выпускать Release без отдельной явной команды пользователя.
   Переписывание истории, force-push и разрушительная очистка также не разрешены
   обычным поручением исправить код. Конфликт решать в пределах задачи с сохранением
   обеих сторон; если решение меняет продуктовый смысл, требуется уточнение.

## Тело PR

Краткая содержательная основная часть: `## Цель`, `## Изменения`, `## Проверки`
и `## CI`. Указать проблему и результат, существенные решения, решение о версии,
реально выполненные проверки и ограничения. В CI — состояние проверок GitHub
актуального HEAD, отдельно от локальных проверок. Не копировать транскрипт команд.

При необходимости объёмные технические доказательства вынести в Gist после
проверки конфиденциальности; в PR оставить выводы и ссылку. Secret Gist доступен
по ссылке и не является приватным хранилищем. Контакты, посты, локальные данные,
секреты и сырой чувствительный вывод не публиковать ни там, ни в PR. Без безопасного
очищенного материала оставить доказательства локально и указать ограничение.
Gist не создавать, если достаточно тела PR.

Если поручен CodeRabbit, его итог в PR — только компактная таблица с ревизией,
режимом, завершённостью, подтверждёнными/отклонёнными замечаниями и исправлениями;
проверки остаются в `Проверки`, состояние GitHub — в `CI`.
Отдельного файла состояния агента или журнала публикации не создавать.
