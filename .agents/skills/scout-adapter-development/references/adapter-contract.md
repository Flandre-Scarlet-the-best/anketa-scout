# Процедура разработки адаптера

## 1. Проверить источник

Определить разрешённый формат API/HTML, стабильность, авторизацию, лицензии и ограничения доступа. Зафиксировать исходную схему на тестовых/публично разрешённых данных, но не публиковать посты и контакты. Проверять ссылку, host, board/thread, OP, даты, номера, вложения и pagination. Если формат неизвестен, сначала исследовать, не писать выдуманную реализацию.

## 2. Сохранить границу слоёв

- `transport` — ограниченная сеть, таймауты, редиректы, отмена, ошибки.
- `source` — формат, происхождение, идентичность записи, безопасная нормализация.
- `domain` — единый предметный критерий анкеты, собственный контакт, канонизация, отклонения.
- `application` — связывание источника, предметной модели и выдачи результата.
- `output` — отображение без утечек управляющих последовательностей/контактов в ошибках.

Не создавать один гигантский парсер, который одновременно делает HTTP, классификацию и рендер. При несовместимом формате изменить общий контракт явно и проверить прежний адаптер.

## 3. Проверить отрицательные случаи

Синтетические тесты на пустой/невалидный ответ, частичную выгрузку, дубли, OP, цитаты, чужие контакты, вложения, неверный URL/host, лимит размера/времени, ошибки авторизации, отказ, отмену и повторный запуск. Проверить сохранение исходного текста отдельно от очищенного представления; не терять доказательство происхождения. Не подменять ошибки пустым списком.

## 4. Прогнать настоящую реализацию

Обычный набор проверок берётся из `VERIFICATION.md`. При изменениях внешнего формата уместен отдельный `scout-live-testing` по согласованному доступному источнику. Связать наблюдаемое поведение с точным бинарником, не публиковать конфиденциальные данные.

## 5. Зафиксировать границы

В PR перечислить проверенные форматы, исключения, ложные срабатывания/отклонения, сохранённые инварианты, результаты и область, которая осталась недоступной. Отдельно дать матрицу Windows, Linux и macOS со статусом фактической проверки и известными платформенными ограничениями; не выводить поддержку остальных платформ из проверки на одной. Не заявлять полную поддержку сайта по одному частному снимку.
