# Процедура реальной приёмки

## 1. Сформулировать проверяемое утверждение

Зафиксировать точную ревизию или путь бинарника, команду сборки, конкретный изменённый путь, платформу и желаемый эффект. Разделять синтетический `cargo test`, настоящий CLI на синтетическом HTTP, локальный фиксированный снимок и сетевой запрос к живому сайту. В отчёте не смешивать эти классы доказательств.

## 2. Подготовить среду

- Выбрать изолированный временный каталог вне репозитория для собственных вспомогательных файлов; проверить реальное местоположение и права.
- Данные реального источника не включать в отслеживаемые файлы, PR, Gist, публикуемые логи, сообщения агента и сторонние API.
- Зафиксировать исполняемый бинарник и связь его сборки с исходниками. `HEAD` сам по себе не подтверждает, что запущен новый бинарник.
- Установить ограничение времени, размера входа и количества запросов; контролировать ошибки, завершение и очистку.
- Не использовать существующие личные конфиги/локальные снимки как тестовые fixtures без отдельного разрешения.

## 3. Выполнить реальный путь

Для CLI проверить `--help`, `--version` и штатное выполнение; зафиксировать stdout/stderr, код выхода и побочные эффекты без раскрытия содержимого. При парсинге на реальном URL убедиться в идентичности board/thread, фактическом ответе и корректности отказов. Для входов использовать синтетические имена и контакты.

По затронутой области проверить:
- невалидный JSON/HTML, отсутствующий OP, неполный ответ, чужой parent, дубли номеров;
- HTTP 4xx/5xx, редирект на чужой адрес, превышение лимита, зависание, таймаут, отмену и BrokenPipe;
- цитаты/чужие контакты, географические совпадения, недоверенную разметку;
- Unicode/узкие терминалы, ANSI/OSC/bidi, многострочные ячейки, цветовые режимы, redirected stdout;
- отсутствие утечки контактов/текста в диагностике.
Покрывать только доступные сценарии и честно отмечать остальные.

## 4. Сравнить и классифицировать

`PASS` — наблюдалось выполнение именно проверяемой реализации с ожидаемыми признаками. `FAIL` — наблюдалось нарушение. `INCOMPLETE` — недоступный источник, инструмент, платформа или доказательства идентичности исполнения. Не превращать «процесс завершился с кодом 0» автоматически в «классификатор корректен».

Сравнение поведения на реальном снимке требует одного и того же локального неизменяемого файла до/после и проверки SHA-256. Нельзя подменять улучшение качества простым ростом числа принятых постов: нужны регрессии и независимое содержательное подтверждение на обезличенных кейсах.

## 5. Уборка и отчёт

Остановить собственные процессы, освободить порты, удалить **только** созданные временные артефакты. Не чистить чужой кэш, профили или пользовательские данные.

Сообщить проверенный SHA/бинарник, источник доказательства (синтетика/снимок/живой сайт), команды/метод, результат, существенные числа без контактов и предел доказательства. Публикация результатов через `scout-git-workflow`, если отдельно поручена.
